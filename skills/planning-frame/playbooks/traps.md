# Traps — framing

- **The request names a solution**: "we need a queue" is an answer wearing a question's clothes. Frame the problem the queue would solve, then let `planning-options` decide whether it is a queue.
- **Goals written as activities**: "migrate to Postgres" is work, not a goal. The goal is what becomes true afterward. If nothing becomes true, question the work.
- **Success criteria copied from the goal**: `G-1: faster search` / `SC-1: search is faster` is a defect. The criterion must contain a number and a way to read it.
- **Skipping non-goals because "it's obvious"**: what is obvious to the framer is exactly what the implementer will add.
- **Deadline treated as a constraint without checking its source**: dates that trace to nothing are soft. Mark them soft — a fake hard deadline distorts every downstream estimate.
